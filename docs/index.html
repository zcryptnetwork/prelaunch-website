Developers

Launch a node. The reference chain is already running.

zcrypt-1 is the public network. You can watch it, point a wallet at it, or sync a validator and bond it. A local Docker stack is a separate chain for experiments. It is not a second copy of the coins on the public network.

Talk to the chain that is already up

The explorer and the RPC are the public doors. The explorer shows each transaction's program and re-checks what it can re-check from public data. It does not show the sender, the receiver, the asset, or the amount of a shielded payment.

A one-line liveness check against the public RPC:

curl -s https://rpc.zcrypt.network/status

The JSON field result.node_info.network is the chain id. result.sync_info.latest_block_height is the tip. Wallet and bridge traffic that carries proofs needs a large body limit. The public edge already allows it. A raw CometBFT port on the open internet is not how wallets should connect. Use the HTTPS RPC.

A first session with the wallet

Download the installer from the homepage. It selects the file for the computer you are using, from the latest public GitHub release of echelonlabsresearch/ZCrypt.

  1. Install it. macOS is an Apple Silicon disk image. Linux ships an AppImage and a deb. Windows ships an NSIS setup.exe that is not Authenticode-signed.
  2. Open Settings and set Consensus Node to https://rpc.zcrypt.network.
  3. Tor is on by default and fail-closed. The wallet reaches the node only through a local Tor proxy at 127.0.0.1:9050. If that daemon is not running, turn Tor off for this session, or start Tor and leave the switch on.
  4. Create a wallet and write down the 24 words. Those words restore normal addresses and the change they derive. They do not restore a bearer file, and they do not restore a stealth address that was made with a fresh key.
  5. Press Refresh after a payment. The wallet scans blocks and trial-decrypts notes.

The public chain has no faucet. You can receive ZCRYPT, or any issued asset, from someone else's payment. A bearer file carries its own fee, so the receiver does not need a balance. Locking Bitcoin and receiving shielded zBTC does not charge ZCRYPT. Redeeming zBTC back to Bitcoin does not charge ZCRYPT either. Sending a coin inside the pool, swapping it, registering an asset, or creating a bearer all burn 0.01 ZCRYPT. A ZCRYPT coin pays that from itself, inside the same proof, so one coin is enough to send and the change comes back to you. A wallet that arrived holding only zBTC can hold it, redeem it, and swap it for ZCRYPT with no ZCRYPT on hand: the side giving ZCRYPT locks first and pays the gas for both legs. Sending zBTC to another pool address still needs a little ZCRYPT for the gas note.

On Receive, drop zcrypt-bearer.txt or paste it. The first line must be exactly zcrypt-bearer/1, then a coin line and a gas line. The first sweep in a block takes the file. On Send, choose bearer coin and the wallet writes the file. Creating one costs 0.03 ZCRYPT on top of the value you put in the file. Hand the file over the way you would hand over cash, then delete your copy.

Run a local playground

This is a private chain on your machine. Coins minted here do not exist on zcrypt-1. You need Docker and Docker Compose v2. The first image build compiles the prover and takes a few minutes.

git clone https://github.com/echelonlabsresearch/ZCrypt.git
cd ZCrypt/chain
cp .env.example .env

Edit .env before you start. A local playground is the devnet feature plus Bitcoin regtest. Leave ABCI_FEATURES empty only when you mean a production build. An empty feature set has no faucet, requires a foundation address, and refuses regtest.

ABCI_FEATURES=devnet
ZCRYPT_BTC_NET=regtest

Then:

docker compose up --build -d

Add --profile dev when you also want the regtest bitcoind that the bridge demo uses. Add --profile bridge only after you understand the reserve-key instructions in chain/.env.example. The reserve key is a file in secrets/, mode 0600, and it never belongs in .env.

State lives on a Docker volume. docker compose down keeps it. docker compose down -v deletes it.

Point a wallet at http://127.0.0.1:36657 and turn Tor off for localhost. The devnet build is the one whose Fund button can mint test coins with the 0x56 faucet. That faucet does not exist on zcrypt-1.

The local compose chain id is also the string zcrypt-1. It is still a different chain: different genesis, different coins. Use a fresh wallet for it. The wallet pins the first chain it connects to and refuses to sign for a node that reports a different chain id. The same id string will not save you from mixing two genesis files in your head.

A three-validator devnet

The bundled stack runs three consensus nodes over one state machine. Each one verifies the shielded proofs. They have to agree on the app hash.

cd ZCrypt/chain
docker compose -f e2e/docker-compose.3node.yml up --build -d

The full live driver stands the stack up, runs the product flows, and tears it down:

KEEP=0 ./chain/e2e/run-all.sh

The fast suite, from a Rust checkout with the pinned nightly, is cd impl && cargo test --workspace. CI on every push runs the same tests in shards, plus Clippy, cargo audit, cargo deny, and the wallet. The three-node job runs on main, nightly, and when someone starts the workflow.

Join the public chain as a validator

A validator is a full node plus a bond. Syncing does not require a bond. Producing blocks does. The plug-and-play file is chain/docker-compose.validator.yml in the protocol repo. From a clone:

cd ZCrypt/chain
docker compose -f docker-compose.validator.yml up -d
docker logs -f zcrypt-validator-cometbft

The entrypoint downloads genesis from the public foundation and finds a seed peer. You do not hand-edit genesis. Until you bond, the process is a syncing full node.

Pin the genesis you actually synced

The foundation node writes config/genesis.sha256 at first start. Put that 64-hex digest in a .env beside the compose file as GENESIS_SHA256. The entrypoint then refuses any genesis whose hash differs. Read the digest from a node you already trust, or from the foundation operator. Do not take it from a random paste.

Verify the image before you bond

The compose file pins the ABCI image by digest. The publish workflow signs that digest with keyless cosign. Check it once:

IMG=$(grep -o 'ghcr.io/[^ ]*@sha256:[0-9a-f]*' docker-compose.validator.yml | head -1)
cosign verify "$IMG" \
  --certificate-identity-regexp '^https://github.com/echelonlabsresearch/ZCrypt/\.github/workflows/image\.yml@refs/tags/v' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

That identity is what the publish workflow puts in the job summary. Use the line it prints if it ever differs. If verification fails, do not run the image. A digest does not move when a tag moves. To build from source instead, set ZCRYPT_ABCI_IMAGE to a local tag as validator.env.example describes. The Dockerfile uses the same pinned nightly and --locked build.

The validator RPC binds to 127.0.0.1:56657 unless you set VALIDATOR_RPC_BIND. P2P port 56656 has to be reachable by peers. Opening the raw RPC on a public address is a separate decision. Wallets should keep using https://rpc.zcrypt.network.

Stop and keep the identity with docker compose -f docker-compose.validator.yml down. Add -v only when you mean to delete that validator's state and keys.

Bond, claim, unbond, delegate

The minimum bond is 10,000 ZCRYPT, taken from a shielded balance. The bond spends those coins into a burn. The stake is real. Voting power is the stake in whole ZCRYPT. On the next block the node joins the active set. Rewards accrue every 100 blocks and are withdrawn with a claim into a fresh private coin.

The consensus private key never goes in the wallet. It stays in the validator's priv_validator_key.json.

  1. In the wallet, Rewards, Become a validator. Enter the stake and the commission. Prepare bond. The wallet shows the chain id, the reward address, the stake in base units, the commission in basis points, and the nonce.
  2. On the validator host, extract the seed and sign. The seed is the first 32 bytes of the consensus private key. Anyone who has it can equivocate your validator and get it slashed. Do not paste it into a chat or into the desktop wallet.
export VALIDATOR_SEED_HEX=$(docker exec zcrypt-validator-cometbft \
  cat /cometbft/config/priv_validator_key.json \
  | python3 -c "import sys,json,base64; print(base64.b64decode(json.load(sys.stdin)['priv_key']['value'])[:32].hex())")

cargo run --release -p zcrypt-bridge --bin bond_validator -- sign \
  --chain-id zcrypt-1 \
  --reward <reward address hex> \
  --stake <base units> \
  --commission-bps <bps> \
  --node http://127.0.0.1:56657

Paste the 128-hex signature back into the wallet and submit. Confirm the set afterwards:

curl -s 'http://127.0.0.1:56657/abci_query?path="/staking/validators"'

A headless alternative, chain/validator-bond.sh, reads the key inside the container and bonds to a reward address the wallet already prepared. Pass the RPC and a stake if you are not on the defaults: ./validator-bond.sh http://127.0.0.1:56657 20000.

Unbond

An unbond sets voting power to zero on the next block. The stake stays locked for 10 days, then becomes claimable. Equivocation, a double-sign that CometBFT reports, burns 5% of the pledged stake and tombstones the key. The slash also reaches into the unbonding queue. The remaining 95% still waits out the 10 days.

Delegate

You can back someone else's validator without running a node. In the wallet, Rewards, Delegate. Your coins are pledged the same way. You raise that validator's power, you earn a share of its rewards after its commission, and you share its slashing risk. Undelegate drops the power immediately and starts the same 10-day wait. Only the key that delegated can undelegate.

Claims pay two streams into the Rewards tab. Block rewards are ZCRYPT. Bridge-fee yield is denominated in the bridged asset itself, split by stake. A claim takes the whole claimable balance of that stream. Balances under 1 ZCRYPT keep accruing. The chain refuses a dust claim so a third party cannot force a tiny coin onto you.

The canonical write-up, including the message the consensus key signs, is chain/README-validator.md. The mechanics of bond, unbond, and delegate are in running.md.

Build the wallet from source

The wallet is a Tauri and React desktop app. You need Node.js 20 or newer and Rust. The nightly is pinned by wallet/rust-toolchain.toml, so a plain cargo in that directory selects it. macOS and Windows use the system webview. Linux needs libwebkit2gtk-4.1-dev, libgtk-3-dev, librsvg2-dev, and libayatana-appindicator3-dev.

cd ZCrypt/wallet
npm install
npm run tauri:dev
npm run tauri:build

tauri:dev compiles the Rust backend on first launch. Release bundles land in wallet/src-tauri/target/release/bundle/. npm run dev is the web UI alone, with no chain behind it.

Published installers are built by wallet-release.yml on a v* tag. The Mac job notarizes and staples the disk image. The checksum job refuses to finish unless the release has a dmg, a deb, an AppImage, and a Windows -setup.exe.

Supply, fees, and the pool

The cap is 21,000,000 ZCRYPT. Twenty percent is the foundation allocation, 4,200,000. Of that, 50,000 is liquid at genesis. Twenty-five percent unlocks at month 12, then monthly through month 48. Eighty percent is mined: 0.14 ZCRYPT per block, halving every 60,000,000 blocks, with rewards paid every 100 blocks. Blocks are one second apart.

A shielded payment burns 0.01 ZCRYPT. A ZCRYPT payment is one proof: its first output is that burn, revealed so anyone can check it, and the other two outputs are the payment and the change. A payment of any other asset is two proofs, the payment proof with a zero fee and a ZCRYPT gas proof carrying the same burn. One-input spends are padded so the chain always sees two inputs and three outputs.

Issuance registers a ticker, a precision, and a hard cap. Further mint is an M-of-N authorization over that exact mint. The wallet uses a 1-of-1 key from the seed. zBTC has no signer set. A Bitcoin proof is the gate. The depositor's shielded coin is the locked amount net of a 10 basis-point fee. That fee accrues to stakers in zBTC. The Bitcoin lock itself is a public Bitcoin transaction. The coin that lands in the pool is an ordinary shielded coin. The swap record of an in-pool trade is also public about that trade's amount, asset, and the keys of the two sides. The payments that funded the escrow, and the payments that take the proceeds away, are ordinary pool payments.

What this does not claim

  • The value layer is post-quantum. Block ordering is CometBFT, and its consensus signatures are classical. The Bitcoin reserve is Bitcoin's signature scheme. Those two cannot forge a shielded coin.
  • A shielded payment is accepted because the STARK verifies. The seven-opcode program is the specification, the wallet's pre-broadcast check, the differential test, and what the explorer shows. Consensus does not re-execute that program over the secret values. It does not have them.
  • The Lean proofs cover conservation, including the field-arithmetic wrap that has inflated other hidden ledgers. They are a hand-written model. They do not prove FRI, Poseidon2, ML-KEM, or ML-DSA, and they do not extract the Rust.
  • There has not been an external audit of the circuit. Treat that as the dominant limit on how much value you point at the chain. An internal review fixed issues it found. The open item is the outside review.
  • The pool hides a spend among the coins the pool has ever held. Early on, that crowd is small. Nullifiers show that spends happen. Staking, claims, mints, bridge escrows, and in-pool swaps name the key they act for. A node sees the submitter's IP unless Tor is on.
  • The Johnson bound the node enforces is 132 bits. A higher figure you may see in the proof parameters is a list-decoding conjecture, not the floor the node checks.
