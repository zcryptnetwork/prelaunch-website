Running ZCrypt:
the public chain and your own.

zcrypt-1 is the public network. This page covers how to query it, how to connect a wallet, how to run a validator on it, and how to start a local chain with Docker for development. Coins on a local chain have no relation to coins on zcrypt-1.

Querying the public chain

There are two public endpoints: the explorer and the RPC. The explorer displays each transaction's program and re-verifies whatever can be verified from public data. For a shielded payment that excludes the sender, the receiver, the asset and the amount, because none of them are on the chain.

EndpointAddress
Explorerhttps://explorer.zcrypt.network
RPChttps://rpc.zcrypt.network
Chain idzcrypt-1
P2PThe foundation seed serves peers on port 26656. The validator compose file discovers it.
Protocol sourcegithub.com/echelonlabsresearch/ZCrypt

To check that the chain is up:

curl -s https://rpc.zcrypt.network/status

In the response, result.node_info.network is the chain id and result.sync_info.latest_block_height is the current height. Wallets and the bridge send proofs of a few megabytes, and the HTTPS endpoint is configured with a body limit large enough for them. Wallets should use the HTTPS RPC rather than a raw CometBFT port.

Setting up the wallet

The homepage download button picks the installer for your operating system from the latest public GitHub release of echelonlabsresearch/ZCrypt.

  1. Install it. The macOS build is an Apple Silicon disk image, Linux has an AppImage and a deb package, and Windows has an NSIS setup.exe that is not Authenticode-signed.
  2. Open Settings and set Consensus Node to https://rpc.zcrypt.network.
  3. Tor is on by default, and the wallet refuses to connect without it. It expects a local Tor proxy at 127.0.0.1:9050. If you do not run one, either start Tor or turn the setting off.
  4. Create a wallet and write down the 24 words. The seed restores normal addresses and the change coins derived from them. It does not restore bearer files or stealth addresses that were generated with a fresh key.
  5. After a payment, press Refresh. The wallet scans new blocks and trial-decrypts the notes in them.

There is no faucet on the public chain. The ways to obtain coins are to receive a payment from someone, to claim a bearer file (which carries its own fee, so an empty wallet can claim one), or to lock Bitcoin and receive zBTC, which costs no ZCRYPT. Redeeming zBTC back to Bitcoin is also free of ZCRYPT. Everything else that moves value burns 0.01 ZCRYPT: sending inside the pool, swapping, registering an asset, and creating a bearer file. When the coin being sent is ZCRYPT, the fee is taken from that coin inside the same proof, so a single coin is enough to send and receive change. A wallet holding only zBTC can hold it, redeem it, or swap it for ZCRYPT without any ZCRYPT, because in a swap the ZCRYPT side locks first and pays the gas for both legs. Sending zBTC to another pool address does require a small amount of ZCRYPT for the gas note.

To claim a bearer file, drop zcrypt-bearer.txt onto the Receive screen or paste its contents. The format is a first line of exactly zcrypt-bearer/1, followed by a coin line and a gas line. If several wallets try to claim the same file, the first claim included in a block wins. To create one, choose the bearer coin option on Send; the wallet writes the file. Creating a bearer costs 0.03 ZCRYPT in addition to the value placed in it. Treat the file as cash: once you have handed it over, delete your copy.

Running a local chain

The Docker stack starts a private chain on your machine. It needs Docker and Docker Compose v2. The first build compiles the prover and takes several minutes.

git clone https://github.com/echelonlabsresearch/ZCrypt.git
cd ZCrypt/chain
cp .env.example .env

Edit .env before starting. For a local chain, enable the devnet feature and use Bitcoin regtest. An empty ABCI_FEATURES produces a production build, which has no faucet, requires a foundation address, and refuses to run against regtest.

ABCI_FEATURES=devnet
ZCRYPT_BTC_NET=regtest

Then:

docker compose up --build -d

Add --profile dev to also start a regtest bitcoind for the bridge. The --profile bridge option starts the bridge watcher and needs a reserve key; read the instructions in chain/.env.example first. The reserve key is stored as a file in secrets/ with mode 0600, never in .env.

curl -s 'http://127.0.0.1:36657/abci_query?path="/commit/count"'

Chain state is kept on a Docker volume. docker compose down preserves it and docker compose down -v deletes it.

Point a wallet at http://127.0.0.1:36657 with Tor turned off. On a devnet build the wallet's Fund button mints test coins through the 0x56 faucet transaction, which the public chain rejects.

The local chain uses the same chain id string, zcrypt-1, but it has its own genesis and its own coins. Use a separate wallet for it. The wallet pins the chain id of the first node it connects to and refuses to sign for a node that reports a different one, but it cannot tell two chains with the same id apart, so do not point one wallet at both.

A three-validator local network

A second compose file runs three consensus nodes, each with its own copy of the state machine. Every node verifies every shielded proof, and the nodes must agree on the app hash at each block.

cd ZCrypt/chain
docker compose -f e2e/docker-compose.3node.yml up --build -d
NodeRPC
node0http://127.0.0.1:46657
node1http://127.0.0.1:46667
node2http://127.0.0.1:46677

The end-to-end driver starts this network, runs the product flows against it, and shuts it down:

KEEP=0 ./chain/e2e/run-all.sh

The unit and integration tests run with cd impl && cargo test --workspace using the pinned nightly toolchain. CI runs the same tests on every push, in shards, together with Clippy, cargo audit, cargo deny and the wallet build. The three-node job runs on pushes to main, nightly, and on manual dispatch.

Running a validator on the public chain

A validator is a full node with a bond. Any node can sync without a bond; only bonded nodes produce blocks. The whole flow is driven from the wallet and one compose file, chain/docker-compose.validator.yml in the protocol repository, and it has three steps: copy the validator identity from the wallet, start the node, bond it.

1. Copy the identity from the wallet

The wallet holds a validator identity, an ed25519 consensus key derived from the recovery phrase, so it restores with the phrase. In the wallet, open Rewards, then Run a validator, then Node setup, and click Copy the .env line. Paste that one line into a .env file next to the compose file:

VALIDATOR_KEY=eyJhZGRyZXNzIjoi…   # one line, from the wallet

Do this before the node starts for the first time. The entrypoint installs the line as the node's priv_validator_key.json, and CometBFT keeps an existing key, so the node signs blocks with the wallet's identity from then on. The line is the signing key: keep the file private and treat it like the recovery phrase. If the node has already started and generated its own key, stop it with down -v, add the line, and start again.

The chain requires every bond and unbond to be signed by the node's consensus key. When the wallet creates that key and the node imports it, staking is a button in the wallet. When the node invents the key instead, every staking action needs a signature produced on the server, which is the fallback described under bonding below.

2. Start the node

cd ZCrypt/chain
docker compose -f docker-compose.validator.yml up -d
docker logs -f zcrypt-validator-cometbft

The compose defaults point at the foundation node. The entrypoint installs the key from .env, downloads the genesis file from the foundation RPC, discovers a seed peer, and syncs. No manual editing of the genesis is needed. Until you bond, the node runs as a syncing full node.

Pinning the genesis hash

The foundation node writes config/genesis.sha256 when it first starts. Put that 64-character hex digest in the same .env as GENESIS_SHA256, and the entrypoint will refuse any genesis file whose hash differs. Obtain the digest from a node you already trust or from the foundation operator, not from an unverified source.

Verifying the image

The compose file pins the ABCI image by digest, and the publish workflow signs that digest with keyless cosign. To verify it:

IMG=$(grep -o 'ghcr.io/[^ ]*@sha256:[0-9a-f]*' docker-compose.validator.yml | head -1)
cosign verify "$IMG" \
  --certificate-identity-regexp '^https://github.com/echelonlabsresearch/ZCrypt/\.github/workflows/image\.yml@refs/tags/v' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

The certificate identity is printed in the publish workflow's job summary; if it ever differs from the line above, use the printed one. If verification fails, do not run the image. Because the image is pinned by digest, moving a tag does not change what you run. To build from source instead, set ZCRYPT_ABCI_IMAGE to a local image tag as described in validator.env.example. The Dockerfile uses the same pinned nightly and a --locked build.

The validator's RPC binds to 127.0.0.1:56657 unless VALIDATOR_RPC_BIND says otherwise. The P2P port, 56656, must be reachable by peers. Exposing the raw RPC on a public address is optional and not needed for wallets, which should keep using https://rpc.zcrypt.network.

docker compose -f docker-compose.validator.yml down stops the node and keeps its identity and state. Adding -v deletes both.

3. Bond it from the wallet

Back in Rewards, Run a validator, enter the stake and the commission and click Bond. The wallet signs the bond with the validator key it holds, so there is no step on the host. The card shows whether the node is signing blocks within a few blocks of the bond. Details of the bond, rewards, unbonding and delegation follow.

Bond, claim, unbond, delegate

The minimum bond is 10,000 ZCRYPT, paid from a shielded balance. Bonding spends the coins into a burn, so the stake is locked rather than merely marked. Voting power equals the stake in whole ZCRYPT. The node joins the active set on the next block. Rewards accrue every 100 blocks and are withdrawn with a claim transaction that produces a new private coin.

With the wallet-owned key from step 1 above, bonding and unbonding are wallet buttons. The fallback below is for a node that generated its own key: that key stays in the validator's priv_validator_key.json and the bond must be signed on the host.

  1. In the wallet, open Rewards, then Become a validator. Enter the stake and the commission and choose Prepare bond. The wallet displays the chain id, the reward address, the stake in base units, the commission in basis points, and the nonce.
  2. On the validator host, extract the seed and sign the bond. The seed is the first 32 bytes of the consensus private key. Anyone holding it can make your validator double-sign and get it slashed, so keep it on the host and do not paste it into a chat or the desktop wallet.
export VALIDATOR_SEED_HEX=$(docker exec zcrypt-validator-cometbft \
  cat /cometbft/config/priv_validator_key.json \
  | python3 -c "import sys,json,base64; print(base64.b64decode(json.load(sys.stdin)['priv_key']['value'])[:32].hex())")

cargo run --release -p zcrypt-bridge --bin bond_validator -- sign \
  --chain-id zcrypt-1 \
  --reward <reward address hex> \
  --stake <base units> \
  --commission-bps <bps> \
  --node http://127.0.0.1:56657

Paste the 128-character hex signature into the wallet and submit. To confirm the validator set afterwards:

curl -s 'http://127.0.0.1:56657/abci_query?path="/staking/validators"'

For a headless setup, chain/validator-bond.sh reads the key inside the container and bonds to a reward address prepared in the wallet. It takes the RPC and the stake as arguments when the defaults do not apply: ./validator-bond.sh http://127.0.0.1:56657 20000.

Unbonding

An unbond sets the validator's voting power to zero on the next block. The stake remains locked for 10 days and then becomes claimable. If CometBFT reports a double-sign, 5% of the pledged stake is burned and the key is permanently removed; this applies to stake in the unbonding queue as well, and the remaining 95% still waits out the 10 days.

Delegating

To stake without running a node, delegate to an existing validator from Rewards, then Delegate, in the wallet. The coins are pledged in the same way as a bond. Delegation adds to that validator's voting power, earns a share of its rewards after commission, and carries the same slashing risk. Undelegating removes the power immediately and starts the same 10-day wait, and only the key that delegated can undelegate.

The Rewards tab shows two claimable streams: block rewards in ZCRYPT, and bridge-fee yield denominated in the bridged asset and divided by stake. A claim always withdraws the whole claimable balance of a stream. Balances below 1 ZCRYPT keep accruing until they pass that threshold, because the chain rejects dust claims; this prevents a third party from forcing a tiny coin into your wallet.

The full reference, including the exact message the consensus key signs, is chain/README-validator.md. The bond, unbond and delegate transactions are described in running.md.

Building the wallet from source

The wallet is a Tauri application with a React front end, built for desktop and iPhone. It requires Node.js 20 or newer and Rust. The nightly toolchain is pinned in wallet/rust-toolchain.toml, so cargo selects it automatically in that directory. macOS and Windows use the system webview; Linux needs libwebkit2gtk-4.1-dev, libgtk-3-dev, librsvg2-dev and libayatana-appindicator3-dev.

cd ZCrypt/wallet
npm install
npm run tauri:dev
npm run tauri:build

tauri:dev compiles the Rust backend on first launch. Release bundles are written to wallet/src-tauri/target/release/bundle/. npm run dev serves the web UI alone, without a backend.

Published installers are built by wallet-release.yml whenever a v* tag is pushed. The macOS job notarizes and staples the disk image, and the checksum job fails unless the release contains a dmg, a deb, an AppImage and a Windows -setup.exe.

Supply and fees

The supply cap is 21,000,000 ZCRYPT. Twenty percent, 4,200,000 ZCRYPT, is allocated to the foundation. Of that, 50,000 is liquid at genesis, 25% unlocks at month 12, and the remainder vests monthly until month 48. The other 80% is issued as block rewards of 0.14 ZCRYPT per block, halving every 60,000,000 blocks, paid out every 100 blocks. Blocks are one second apart. The vesting schedule is enforced by consensus, the amount claimed so far is part of the state hash that every validator signs, and the explorer shows the vested and claimed totals.

A shielded payment burns 0.01 ZCRYPT. A payment in ZCRYPT is a single proof whose first output is the burn, revealed so that anyone can check it, with the payment and the change as the other two outputs. A payment in any other asset is two proofs: the payment proof with a zero fee, and a separate ZCRYPT gas proof carrying the burn. Spends with one input are padded to two, so every transaction has the same shape on the chain: two inputs and three outputs.

Registering an asset fixes its ticker, its precision and a hard cap. Each further mint requires an M-of-N authorization over that specific mint; the wallet uses a 1-of-1 key derived from the seed. zBTC has no signer set, because its mint is gated by a Bitcoin proof instead. A depositor receives a shielded zBTC coin for the locked amount less a 10 basis point fee, which accrues to stakers in zBTC. The Bitcoin side of a deposit is an ordinary public Bitcoin transaction, while the zBTC coin that results is an ordinary shielded coin. An in-pool swap publishes the amount, the asset and the keys of both parties for that trade; the payments that fund the escrow and the payments that collect the proceeds are ordinary shielded payments.

Limitations

  • The value layer uses post-quantum cryptography. Block ordering is CometBFT, whose consensus signatures are classical, and the Bitcoin reserve uses Bitcoin's signature scheme. Breaking either of those would not allow a shielded coin to be forged.
  • A shielded payment is accepted when its STARK proof verifies. The seven-opcode program serves as the specification, as the wallet's check before broadcast, as the differential test against the circuit, and as what the explorer displays. Consensus cannot re-execute that program over the secret values, since it never sees them.
  • The Lean proofs cover value conservation, including the field-arithmetic wraparound that has caused inflation bugs in other private ledgers. They are a hand-written model of the circuit. They do not cover FRI, Poseidon2, ML-KEM or ML-DSA, and they are not extracted from the Rust code.
  • The circuit has not had an external audit. Internal reviews have been done and their findings fixed, but an outside review is still outstanding, and that should be the main consideration in how much value you commit to the chain.
  • The anonymity set of a spend is every coin the pool has ever held, which is small while the chain is young. Nullifiers reveal that spends occur, though not which coins. Staking, claims, mints, bridge escrows and in-pool swaps all name the key they act for. A node sees the IP address of whoever submits a transaction unless Tor is used.
  • The proof soundness the node enforces is 132 bits under the Johnson bound. The higher figure reported in the proof parameters relies on a list-decoding conjecture and is not the floor the node checks.
