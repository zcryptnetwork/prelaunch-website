One minute

Query the chain

Is it up, and how high is it?

curl -s https://rpc.zcrypt.network/status

result.node_info.network is the chain id. result.sync_info.latest_block_height is the current block.

Who is validating?

curl -s 'https://rpc.zcrypt.network/abci_query?path="/staking/validators"'

The explorer shows every transaction's rule program and re-checks whatever can be checked from public data. For a private payment that leaves out the sender, the recipient and the amount, because none of them are on the chain. Of the coin, only one thing shows: whether it was ZCRYPT or some other coin.

About 30 minutes, mostly waiting

Run a validator

A validator is a node with a stake behind it. Any node can follow the chain. Only staked nodes produce blocks and earn rewards.

You needDetail
A serverLinux with Docker and the Compose plugin, online all the time
An open port56656 reachable from the internet (peer-to-peer)
The walletThe desktop wallet, holding at least 10,000 ZCRYPT to stake

  1. Copy your validator key from the wallet

    In the wallet, open Rewards, then Run a validator, then Node setup, and click Copy the .env line. It looks like this:

    VALIDATOR_KEY=eyJhZGRyZXNzIjoi...

    The key comes from your recovery phrase, so it restores with the phrase.

    This line is the node's signing key. Keep it as private as your recovery phrase.

  2. Start the node

    On the server:

    git clone https://github.com/echelonlabsresearch/ZCrypt.git
cd ZCrypt
git checkout mainnet
cd chain/validator
cp .env.example .env

    Open .env and paste your VALIDATOR_KEY=... line into it. Do this before the first start. Then:

    docker compose up -d
docker logs -f zcrypt-validator-cometbft

    The first start compiles the node, which takes several minutes. It then downloads the genesis, finds a peer and syncs. Nothing else needs configuring: the chain id, the seed and the ports are already in the compose file.

    Check progress:

    curl -s http://127.0.0.1:56657/status

    The node has caught up when result.sync_info.catching_up is false.

  3. Stake from the wallet

    Back in the wallet, open Rewards, then Run a validator. Tick that the node is running with this key and has synced. Enter the stake (at least 10,000 ZCRYPT) and your commission, and click Bond.

    The stake leaves your balance and is locked. On the next block your node joins the validator set and starts producing blocks. The same screen shows whether it is signing.

If the node started without your key

It generated a key of its own, and the wallet's Bond button will sign for the wrong one. Wipe it and start again:

docker compose down -v       # deletes the node's key and state
# paste VALIDATOR_KEY=... into .env
docker compose up -d

No server needed

Stake without a node

In the wallet, open Rewards, then Delegate, and choose a validator. Your coins add to that validator's voting power and earn a share of its rewards, less its commission.

  • Delegated coins carry the same 5% penalty if that validator double-signs.
  • Undelegating starts the same 10-day wait. Only the key that delegated can undelegate.
  • Two kinds of reward appear on the Rewards tab: block rewards in ZCRYPT, and a share of bridge fees paid in zBTC.
  • A claim withdraws the whole balance of one kind. Balances under 1 ZCRYPT keep building until they pass it.

For development

Run a local chain

A private chain on your own machine, with a faucet. You need Docker and the Compose plugin. The first build takes several minutes.

git clone https://github.com/echelonlabsresearch/ZCrypt.git
cd ZCrypt/chain
cp .env.example .env

In .env, set these two lines:

ABCI_FEATURES=devnet
ZCRYPT_BTC_NET=regtest

Then start it:

docker compose up --build -d
curl -s http://127.0.0.1:36657/status

Point a wallet at http://127.0.0.1:36657 with Tor switched off. On a devnet build the wallet's Fund button mints test coins.

Use a separate wallet for local chains. A local chain reports the same chain id, zcrypt-1, so a wallet cannot tell it from the real one. Never point one wallet at both.

What CI runs

Test network and tests

Three validators and a regtest Bitcoin, with every real flow driven against them: payments, payment files, staking, swaps, and Bitcoin in and out. It needs Docker and takes about 50 minutes.

KEEP=0 ./chain/e2e/run-all.sh

To keep the network running and poke at it, leave out KEEP=0. The three nodes answer on 127.0.0.1:46657, 46667 and 46677.

The unit and integration tests generate real proofs, so they take minutes. Run them in three parts, as CI does:

cd impl
cargo test --locked -p zcrypt-shield -p zcrypt-core --lib
cargo test --locked -p zcrypt-core --test '*' --examples
cargo test --locked -p zcrypt-abci-node
cargo test --locked -p zcrypt-bridge -p zcrypt-explorer -p zcrypt-cli

The Rust toolchain is pinned in impl/rust-toolchain.toml; cargo installs it on first use. The Lean proofs:

cd formal
lake build && lake env lean Axioms.lean

Tauri and React

Build the wallet

You need Node.js 20 or newer and Rust. On Linux, also install libwebkit2gtk-4.1-dev, libgtk-3-dev, librsvg2-dev and libayatana-appindicator3-dev.

cd ZCrypt/wallet
npm ci
npm run tauri:dev      # run it; the first launch compiles the prover
npm run tauri:build    # make an installer

Installers land in wallet/src-tauri/target/release/bundle/. To work on the interface alone, with a simulated backend:

npm run dev            # then open http://localhost:1420/?mock=1

Enforced by consensus

Supply and fees

RuleValue
Maximum supply21,000,000 ZCRYPT
Block reward0.14 ZCRYPT per block, halving every 60,000,000 blocks, paid out every 100 blocks
Foundation20% (4,200,000). 50,000 liquid at genesis, 25% at month 12, the rest monthly to month 48
Fee per transaction0.01 ZCRYPT at least, destroyed. A swap costs 0.01 or 0.02. Claiming rewards and unstaking are free
Making a payment file0.03 ZCRYPT on top of the amount: 0.02 to create it, 0.01 inside it for the recipient's fee
Bitcoin in0.1% of the deposit, paid to stakers in zBTC. No ZCRYPT needed
Minimum stake10,000 ZCRYPT
Unbonding wait10 days
Double-sign penalty5% of stake destroyed, key removed

A payment in ZCRYPT is one proof: the fee comes out of the coin being sent. A payment in any other coin is two proofs, the payment and a separate ZCRYPT fee. That difference is visible, so an observer can tell a ZCRYPT payment from a payment in another coin, but not which other coin. Within each kind every payment has the same shape, two inputs and three outputs.

The foundation's vesting schedule is checked by every validator, and the explorer shows what has vested and what has been claimed.

Known limits

Limits

  • Post-quantum covers the coins. Block signing is CometBFT's, and the Bitcoin reserve uses Bitcoin's signatures. Breaking either would not let anyone forge a private coin.
  • The Lean proofs are a hand-written model of the circuit's rules. They do not cover the hash function, the proof system or the encryption, and they are not generated from the Rust code.
  • The crowd is every coin the pool has held, which is small while the chain is young. The chain shows that spends happen, not which coins were spent.
  • Some actions name a key: staking, reward claims, mints, bridge escrows and swaps.
  • A node sees the IP address of whoever submits a transaction, unless they use Tor.
  • Proof soundness enforced by the node is 132 bits.
  • An independent external audit is planned. Weigh that when deciding how much value to commit.
