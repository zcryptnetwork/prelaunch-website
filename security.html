Security

Money that cannot be printed.

The rule that nobody can create coins has been proven mathematically and checked by a computer, against the circuit that runs on the network.

The problem

Hidden amounts can hide counterfeiting.

When amounts are hidden, nobody can add them up. So if the rule-checker has a bug, someone could create coins and no one would ever see it happen.

It has happened to private ledgers before, and it is the reason many people do not trust them.

Hidden money cannot be audited by adding it up. The rules have to be proven.

The proof

The rules are proven in Lean.

We wrote the live payment circuit down in Lean 4, a proof assistant: every one of the 40 places where the circuit asserts something. Then we proved that any payment the circuit accepts creates nothing and loses nothing.

Lean checks every logical step. If a single step were missing, the proof would not compile. It compiles, with nothing missing, and it is checked again on every change to the code.

What the theorem says

For any payment the network accepts:

  • The coins going in equal the coins coming out plus the fee, as whole numbers, with no wrap-around trick.
  • Every coin spent really existed in the pool.
  • Every coin spent is marked spent, in exactly one way, so it cannot be spent twice.
  • Each new coin is locked to its value, its coin type and its owner.

Anyone can run the proofs.

They are public and take about fifteen seconds on a laptop.

Verify

Check it yourself.

Install Lean, then:

git clone https://github.com/echelonlabsresearch/ZCrypt.git
cd ZCrypt/formal
lake build                  # checks every proof
lake env lean Axioms.lean   # fails on any unfinished proof or added assumption

You can also watch the rules run on live payments. Open any transaction in the explorer and it shows the checks that payment had to pass.

Testing and review

Tested and reviewed.

Tested

The payment rules exist twice: once as the circuit, and once as a short program a person can read. They are run against each other on valid and hostile inputs, so a difference between what the rules say and what the circuit enforces cannot hide.

Every change is also run on a real three-validator network that exercises each feature end to end, including the Bitcoin bridge.

Reviewed

Since July 2026 the full source has been through eight rounds of adversarial review: each one assumes the system is broken and tries to prove it.

Limits

What is not proven.

The proofs cover one specific claim. These are the things they do not cover.

  • The building blocks are assumptions. The hash function, the proof system and the post-quantum encryption are assumed secure, as they are in every deployed system. The theorems prove the rules and the arithmetic, not the primitives.
  • The model is written by hand. It was transcribed from the code by reading it. A test fails if the circuit's layout drifts from the model, but the circuit model is not yet generated from the code automatically. Only a small core of the readable rule program, its range and balance checks, is extracted from the Rust by tools, and the no-inflation theorem is proved against that extract as well.
  • The proofs cover the money rules. Consensus, networking, the wallet and the bridge are tested and reviewed, not proven.
  • The proofs are about counterfeiting, not privacy. Privacy rests on the proof system's zero-knowledge property and on the size of the crowd.
  • The network is young. It runs on two validators today, with 20,005 ZCRYPT staked between them (the largest stake is 50% of the total). While the set is this small, the foundation's validator carries extra voting weight so the chain keeps running if another validator goes offline. That weight is removed automatically once other validators have staked 1,000,000 ZCRYPT between them with none holding more than a third. Anyone with 10,000 ZCRYPT can run one.
