The most important rule of any currency is that nobody can create it out of thin air. On ZCrypt that rule is not a promise, a policy, or a line in a document. It is a mathematical theorem, checked by a computer, about the exact circuit that runs on the network today.

Level 1

In a minute

For everyone

A ZCrypt payment hides everything: who paid, who was paid, how much, and which coin. That raises an obvious question. If nobody can see the amounts, how does anyone know the money is real? How do you know a payment did not quietly create a million coins?

The answer is that every payment carries a proof. Before the network accepts a payment, it checks that proof, and the proof can only exist if the payment obeyed the rules: the coins going in are worth exactly the coins coming out plus the fee, every coin spent really existed, and no coin is spent twice. The chain checks the rules without ever seeing the numbers.

That shifts the whole question onto the rules themselves. If the rule-checker has a bug, the proof might pass for a payment that invents money, and because the amounts are hidden, nobody would ever notice. In privacy systems this is the nightmare scenario, and it has happened in the real world.

So we did something most projects do not. We wrote the rule-checker down in a language a proof assistant understands, and we proved, step by step, that any proof it accepts describes a payment where nothing was created and nothing was lost. The computer checks every step of that argument. If a single step were missing, the proof would not compile. It compiles, with nothing missing.

What this means for you

The supply of ZCrypt can only ever go down. There are 21 million coins at most, every fee is burned, and the rule that stops anyone from printing more is a theorem, not a trust assumption about the people who wrote the code.

Level 2

How it works

For the technical reader

The seven checks

A shielded transfer on ZCrypt proves one statement with a STARK, a zero-knowledge proof system built only from hashes, with no trusted setup and no elliptic curves. The statement is the same seven checks you can watch run on any transaction in the explorer:

  1. Amounts are real
  2. One coin type per payment
  3. Nothing created, nothing lost
  4. Spent coins are spent
  5. New coins match
  6. Every coin came from the pool
  7. Done

Each check is also written as a small, transparent bytecode program (the auditability VM). Wallets run that program on the real numbers before they build a proof, nodes run it again on the public parts of every transaction, and the proof system enforces it on the hidden parts. The circuit and the VM are tested against each other on thousands of sampled witnesses, valid and adversarial, so a divergence between what the program says and what the circuit enforces cannot hide.

What "formally verified" means here

A STARK circuit is a table of numbers (the trace) and a list of equations (the constraints) that every row of the table has to satisfy. The prover fills in the table, the verifier checks the equations. The production circuit, CoinsAirTall, has 128 rows, 9 hash groups per row, two inputs, three outputs, and 62-level Merkle paths. It has exactly 40 places where it asserts that something is zero.

We transcribed all 40 of those assertion sites, with their row gating, lane layout and public-input offsets, into Lean 4, a proof assistant whose kernel checks every logical step. Then we proved the soundness theorem:

Zcrypt.Air.soundness

Any well-formed trace that satisfies all 40 constraints describes a transfer in which, over the integers, in0 + in1 = out0 + out1 + out2 + fee; every value is a bounded 26-bit integer; each published output commitment is the hash of its value, blind, owner key and asset, with one shared asset; each input's owner key is derived from a spend secret the trace holds; each published nullifier is the one canonical nullifier of that input and nothing else; a dummy input has value zero; and every active input sits under the public Merkle root along a 62-level path.

From that one theorem the protocol's money guarantees fall out as short corollaries: no_inflation, nullifier_canonical, every_input_publishes, dummy_worthless. Lean checks them all. The whole development is 1,563 lines, 82 theorems, zero sorry, and the main theorems depend on nothing but Lean's three standard foundational axioms (propext, Classical.choice, Quot.sound). No Mathlib, no external library: the proofs are discharged by Lean's own omega decision procedure, and the full build, including a kernel-checked primality proof of the field modulus, takes about fifteen seconds on a laptop.

Check it yourself

The proofs live in the public repository under formal/, with a file:line reference into the Rust source on every modeled constraint. To machine-check them:

git clone https://github.com/echelonlabsresearch/ZCrypt
cd ZCrypt/formal
lake build                       # kernel-checks every proof

# confirm nothing depends on sorry
echo 'import Zcrypt
#print axioms Zcrypt.Air.soundness_prop
#print axioms Zcrypt.Carry.conservation_of_limb_constraints' > ax.lean
lake env lean ax.lean
# => depends on axioms: [propext, Classical.choice, Quot.sound]

Lean 4 is installed with elan; the toolchain is pinned in formal/lean-toolchain.

The formal work was built up in three layers, each one closer to the deployed code.

The hash is abstract, on purpose

The circuit hashes with Poseidon2. The Lean model does not re-prove Poseidon2's round constraints; it takes out = H(inp) for an arbitrary function H and proves everything the wiring of those digests implies. Every theorem therefore holds for the real hash, and nothing is assumed about H, not even injectivity. Where a corollary genuinely needs a hash property, the theorem says so explicitly: nfBlock_injective is a statement about the block layout, not about H. This is the honest shape of the claim: constraint and arithmetic correctness are proven unconditionally; collision resistance of the concrete hash is a cryptographic assumption, as it is in every system.

A finding the model caught

Formal models earn their keep when they see what a reader misses. Our circuit review of 26 October 2026 found a medium-severity privacy issue: the inner nullifier block absorbed the blind directly, so a sender who chose a degenerate blind could make that block coincide with the key block and predict the recipient's nullifier, learning when the coin was later spent. The value-level models could not see it because they abstract each field to one integer. The circuit-level model can. Corollaries.inner_nf_eq_pk_iff is that finding stated as a theorem over the fixed layout: after the fix, the two blocks coincide exactly when an inner digest equals a fixed constant, which is a preimage of H and not a free choice. The nullifier function was changed the same day, in both circuits, before genesis.

The proof system's parameters

The STARK ships with one parameter set in every build: 112 FRI queries, 20 bits of proof-of-work grinding, and a rate of 2−2. Fri.lean pins those constants and proves the arithmetic behind the two security figures the code reports: 132 bits under the Johnson bound, which is what the node enforces as its mainnet floor of 128, and 244 bits under the conjectured list-decoding radius. A unit test in the Rust crate fails if the Lean constants and the compiled constants ever drift apart. What Fri.lean does not prove is FRI itself, the Reed-Solomon proximity-gap theorem; that is the programme of ArkLib and our planned next step.

The cryptographic foundation

  • No signatures in the pool. Spend authority is a Poseidon2 preimage, not a discrete-log signature. Proofs are hash-based STARKs with no trusted setup.
  • Post-quantum note encryption. Encrypted notes use ML-KEM-768 (FIPS 203), so a ciphertext recorded today is not waiting to be opened by a future quantum computer.
  • Post-quantum issuance authority. Mint authorizations for bridged and user-issued assets are ML-DSA-65 (FIPS 204) threshold signatures over the complete escrow parameters under a protocol context string, epoch-bound and replay-proof.
  • Canonical encodings. A field element has one serialization anywhere it matters; transaction parsing rejects non-canonical limbs, and nullifier registry keys are computed over reduced forms, which rules out spending a coin twice under two encodings of the same nullifier.
  • Replay and binding. A proof binds a chain-domain tag, an anchor from a bounded root window, and a transaction-binding hash over its ciphertexts, commitments, fee and proof bytes. A proof made for one chain, one state or one transaction cannot be reused for another.
  • Whole-crowd anonymity. Membership is proven by a 62-level Merkle path inside the circuit, so every payment hides among every coin that has ever existed, with no decoy sets to analyse and no tree rollover, ever.
Assurance

Beyond the proofs

Testing and engineering discipline

A theorem covers what it states. Everything around it is covered by tests, and those tests run on every push.

  • Differential testing. The production circuit is checked against an independent wide-trace implementation of the same statement and against the transparent VM, on sampled witnesses, valid and adversarial. The three must agree on every one.
  • Mutation testing of the circuit. Seventeen mutation tests deliberately corrupt a satisfying trace, one cell or one constraint at a time, and assert that the constraint checker rejects it. A constraint that could be removed without a test failing would be a constraint that enforces nothing.
  • Live multi-validator end-to-end. A three-validator network is brought up in CI and driven through the whole product surface: shielded transfers, bearer coins, staking, claims, asset registration, the Bitcoin bridge in both directions, and in-pool swaps, plus an adversarial suite of transactions that must be rejected.
  • Reproducible state. Every node recomputes its state root from its persisted snapshot on start and refuses to run if the root does not match. Consensus folds the commitment tree, the nullifier set, the staking ledger and the validator set into that root.
  • Supply chain. Dependencies are audited and pinned (cargo audit, cargo deny, npm audit), the lint ratchet only tightens, and the macOS wallet is signed and notarized, the Windows installer Authenticode-signed, with checksums published for every artifact.
  • Transparent rules on chain. The explorer runs the auditability VM on every transaction and shows each of the seven checks passing. The rules are not hidden inside the proof; they are readable by anyone.
Review

Adversarial review

Seven rounds and counting

ZCrypt is built by a team with two decades of application security experience, and the project has been reviewed the way we would review anyone else's: by assuming it is broken and trying to prove it. Since July 2026 the full source has been through seven rounds of adversarial, code-only security and privacy review, each run as an independent red-team pass over consensus, the circuit, key management, the bridge, the wallet and the explorer.

RoundScopeOutcome
31 Jul 2026Full system, five parallel red teamsCrypto core found sound. Replayable unbond, permanent bootstrap sentinel and a devnet-default build fixed.
3 Aug 2026Full system, source-only, six reviewersCircuit traced at constraint level: no mint, double-spend or fake-membership path. Front-runnable bridge mint fixed with a depositor authorization.

17 Oct 2026Bridge and swap deep dive, seven parallel readsA chain-halt via a publicly computable settlement blind and a wallet preimage-loss path fixed; escrows auto-expire in consensus.
26 Oct 2026The shield circuits, constraint by constraintNo soundness break. Degenerate-blind nullifier linkage fixed before genesis; the fix is now a theorem; seventeen mutation tests added.

Every critical and high finding from these rounds was fixed, with a test, before the network launched. The protocol will also go through independent external audit; the formal model and the review history above exist so that an outside auditor starts from a precise statement of what is claimed, rather than from scratch.

Boundary

What is not proven

Read this part too

A security page that only lists wins is marketing. Here is the edge of what the theorems cover.

  • The hash and the proof system are assumptions. Poseidon2 collision resistance, FRI query soundness, and the security of ML-KEM and ML-DSA are cryptographic assumptions, as in every deployed system. The theorems prove the constraints and the arithmetic; they do not prove the primitives.
  • Two public inputs sit outside the model. The chain-domain tag and the encrypted-notes digest are bound only through the Fiat-Shamir transcript, not by circuit constraints, so the AIR model has nothing to say about them.
  • The model is a hand transcription. Layout.lean was written from tall.rs by reading it. It is checked against the source by file-and-line provenance, by the mutation tests, and by a test that fails if the compiled constants drift, but it is not yet an automatic extraction. Mechanically extracting the Rust into Lean (Charon, then Aeneas) is the next engagement, and the circuit's heavy use of generic traits is the first obstacle to scope.
  • The proofs cover the money rules, not every line. Consensus, networking, the wallet, the bridge watcher and the explorer are tested and reviewed, not proven. Staking, trade escrows and the Bitcoin bridge are public by design; what is and is not private is written down in plain language.
