ZCrypt is a shielded chain you can use without a centralized exchange. The native coin is ZCRYPT. On top of it, anyone can issue an asset into the same pool, swap it for ZCRYPT or for any other asset on the chain, and hand the result to someone as a file.

01

The listing was the product.

A privacy coin can hide a payment perfectly and still be useless. For years the way to buy one, sell one, or trade it for anything else was a centralized exchange. The exchange sees both sides, keeps the order book, and can close the market whenever it wants. When the listing goes, the coin is still private and nobody can get in or out. The privacy survived. The economy did not.

ZCrypt is built so that door is not required. Every coin of every asset sits in one pool, and a spend hides among every coin that pool has ever held. Issuing an asset, sending it, and exchanging it are protocol actions. They use the same pool, the same proofs, and the same rules as the native coin. An asset you create does not need to be wrapped onto another chain, listed on an exchange, or routed through someone else's swap contract.

Bitcoin can still come in, as shielded zBTC, when you want a door to Bitcoin. An asset issued on ZCrypt does not need that door.

02

The exchange is the chain.

On Ethereum, Solana, and Bitcoin, the coin and the market are different things. The chain moves the coin. A separate service, a centralized exchange or a swap contract deployed by someone else, is where one asset becomes another. That service can go offline, change the rules, freeze a pool, or refuse the asset.

On ZCrypt the trade is two escrows in the protocol. Two people agree on an exchange. Each locks what they are offering, under one shared secret. Revealing the secret settles both sides together. If the time runs out first, each side gets its own coins back. One side can be ZCRYPT. The other side can be ZCRYPT, or any asset someone has issued. There is no order book to host and no outside chain that has to accept the asset first.

The escrow record names the amount and the asset of that particular trade, because the two people have to be able to see what they are locking. Where those coins came from, and where the coins they receive go after the trade, is an ordinary payment in the shared pool. Finding someone to trade with can happen in any chat. The settlement itself does not leave ZCrypt.

03

An asset you invent inherits the coin.

ZCRYPT is the gas and the native money. The unusual layer is the one above it. You register a ticker, a precision, and a supply cap. From then on that asset is minted, sent, swapped, and turned into a bearer file under the same rules as ZCRYPT. The asset identifier sits inside the coin, hidden. A transfer of your asset and a transfer of ZCRYPT publish the same shape of data. The proof checks that a payment does not turn one asset into another.

The cap is fixed when you register. Minting more requires an authorization over that exact mint, signed with a post-quantum signature. The wallet's own flow uses a single key from your seed. zBTC is the exception: nobody's signature mints it. A Bitcoin deposit proof does.

04

Send it like a photo.

A bearer payment is a small text file. You send it the way you send a photo: a chat, an email, a USB stick, a piece of paper. The receiver opens their wallet, drops the file onto Receive, and the value is credited. They can paste it instead. They do not need an address, and they do not need a balance already. The file carries the fee that spends it.

There is no recipient on the chain. The chain learns that two new coins exist in the pool, and later that someone swept them. It does not learn who handed the file to whom. Because every asset shares that pool, the sweep also does not reveal which asset moved or how much. A ZCRYPT bearer and a bearer of an asset you issued are indistinguishable on the wire.

The file is the money until it is claimed. The first sweep takes it. A copy you kept can still spend it until that sweep is in a block. A 24-word restore does not bring the file back. The wallet writes it as zcrypt-bearer.txt, with a coin line and a gas line. A loose coin string on its own is not a payment.

05

The value layer is post-quantum.

The parts that create value, hold value, and move value inside the pool are hash-based or lattice-based from the start. A spend is not a signature. It is knowledge of a secret, proved inside a STARK. STARKs are built from hash functions. There is no trusted setup and no elliptic curve under the coin. Notes are encrypted to ML-KEM keys. Issuing and rotating an asset authority uses ML-DSA.

Two edges stay classical, and both are outside the pool. Ordering blocks uses the consensus signatures of CometBFT. The Bitcoin reserve uses Bitcoin's own signatures, because a lock on Bitcoin cannot use anything else. Neither of those can forge a shielded coin or mint an issued asset.

06

The rules are on the page.

A private chain asks you to trust a proof you cannot read. ZCrypt keeps a second, readable copy of the rules. Every kind of transaction has one short program. The shielded payment's program is seven lines. The proof is a proof that this program passed.

The wallet runs that plain program on the real values before it will broadcast, and it refuses to send if the program and the proof disagree. A test suite feeds the same payments to the program and to the circuit and requires the same answer from both. For bonds, claims, mints, and swaps, the chain runs the program itself.

The explorer shows the program on every transaction. You do not get the sender, the receiver, the asset, or the amount. On a shielded payment the explorer checks the proof and shows the checks that proof covers. On everything else it walks the same program the chain ran.

Shielded paymentseven checks
  1. CHECK_RANGE each amount is in range
  2. CHECK_SINGLE_ASSET one asset in the payment
  3. CHECK_CONSERVATION out equals in, plus the fee
  4. COMPUTE_NULLIFIERS spent coins are marked spent
  5. COMPUTE_OUTPUTS new coins match the published commitments
  6. CHECK_MEMBERSHIP each spent coin is in the pool

That conservation check is machine-checked in Lean, and Lean's kernel accepts it with no unfinished holes. The proofs are a careful model of the arithmetic. They do not prove the hash function, and they are not a claim that every line of the system has been proved. The boundary is written down with the proofs.

Desktop wallet

Download the file for this computer.

The button looks at the public GitHub release and picks the installer for the system you are on. macOS is an Apple Silicon disk image. Linux prefers the AppImage and also lists a deb. Windows is an NSIS setup.

Download First session

Checking the public release.

    1. 1Install and open the wallet. On a Mac, open the disk image. On Windows, run the setup. On Linux, mark the AppImage executable, or install the deb.
    2. 2Point it at the live chain. Settings, Consensus Node, https://rpc.zcrypt.network. The first node you connect defines the chain your signatures bind to.
    3. 3Tor is on by default and the wallet will not talk to the node unless a Tor daemon is listening on 127.0.0.1:9050. Leave it on if Tor is running. Turn it off for a first session on a clear network.
    4. 4Receive needs no prior balance. Someone pays you, or sends a bearer file, and Refresh credits the coins. The public chain has no faucet. Spending an issued asset inside the pool burns 0.01 ZCRYPT as gas, so a wallet that holds only zBTC can redeem it back to Bitcoin and cannot send it in the pool until it holds that gas.

    Published Mac images are Developer ID signed, notarized, and stapled. The Windows installer is not Authenticode-signed, so SmartScreen can warn. Compare every file with SHA256SUMS on the release before you open it. Source build instructions are in the developer docs.

    Watch the chain explorer.zcrypt.network — every transaction, the program, and none of the private fields. Run a node Local playground, or join zcrypt-1 as a validator. Read the paper Cash Is a File.
